# DeepSeek MLA：用低秩潜变量压缩 KV Cache

> 本文是面向 Diy-LLM 第 15 章的前沿技术解读，串联第 4 章的注意力架构与第 10 章的推理内存问题。分析依据 DeepSeek-V2 原始技术报告；文中的容量数字由报告公开的模型尺寸代入公式计算，不是硬件实测。

## 先说结论

标准多头注意力（MHA）会为每个历史 token、每层、每个注意力头保存 Key 和 Value。上下文变长或并发请求增多时，KV Cache 会占用大量显存。DeepSeek 的多头潜在注意力（Multi-head Latent Attention，MLA）把所有头的 Key/Value 联合投影到较小的潜变量，再从潜变量计算注意力；为了保留位置信息，它还单独保存一个共享的 RoPE Key。

因此 MLA 保存的并非“一个不带位置的 latent 就够了”，而是每层、每个历史 token 的 `c_t^KV` 与 `k_t^R`，总元素数为 `(d_c + d_h^R) × 层数`。它的关键收益是把 MHA 中按头保存的两组向量，换成共享的低秩表示；关键代价是增加投影与实现复杂度，并把注意力表达能力约束在压缩维度中。

## 1. 它要解决什么问题

自回归解码时，新 token 要与前文所有 token 做注意力。若每一步都重新计算前文 Key/Value，工作会重复，所以推理引擎把它们留在 KV Cache 中。缓存大小随上下文长度线性增长，也随层数、并发序列数和每个请求的 token 数增长；显存被缓存占用后，可同时服务的请求数也会受限。

对层数为 `L`、注意力头数为 `n_h`、每头维度为 `d_h` 的 MHA，每个 token 需要保存：

```text
KV 元素数 / token = 2 × n_h × d_h × L
```

系数 2 来自 Key 与 Value。权重显存与 KV Cache 是两项不同的开销；本文只计算后者。

## 2. MLA 怎样压缩

对当前层输入 `h_t`，MLA 先用一个下投影得到联合 KV 潜变量：

```text
c_t^KV = W_DKV h_t             # 维度 d_c
k_t^C  = W_UK c_t^KV           # 各注意力头的内容 Key
v_t^C  = W_UV c_t^KV           # 各注意力头的 Value
```

如果只考虑内容，推理缓存可以只保留 `c_t^KV`，而不再为每个头分别保存完整 Key 和 Value。计算注意力时，矩阵乘法的结合律允许把 Key 的上投影合并到 Query 路径，把 Value 的上投影合并到输出投影；这样解码时不必先为每个历史 token 显式还原完整 K/V。实际加速仍取决于推理内核是否按这种布局融合计算。

### 为什么还要单独保存 RoPE Key

位置编码不能简单塞进 KV 潜变量。RoPE 随 token 位置改变；若它施加在上投影后的内容 Key 上，位置相关矩阵会夹在投影矩阵之间，使原有矩阵无法预先合并。解码每生成一个 token，就可能需要为新的位置重新处理整个前缀 Key，抵消缓存压缩的好处。

MLA 将位置信息拆到单独路径：

```text
k_t^R = RoPE(W_KR h_t)        # 每层、每个 token 只生成一个共享位置 Key
k_t,i = [k_t,i^C ; k_t^R]     # 每个注意力头使用自己的内容 Key + 共享位置 Key
```

所以每层、每 token 实际缓存 `c_t^KV` 和 `k_t^R`。若位置通道宽度为 `d_h^R`，总缓存公式为：

```text
MLA 元素数 / token = (d_c + d_h^R) × L
```

这也是理解 MLA 时容易漏掉的一点：RoPE 路径不是免费的，报告中明确将解耦 Key 计入缓存。

## 3. 用 DeepSeek-V2-Lite 的尺寸估算

DeepSeek-V2-Lite 报告给出的配置是 27 层、16 个注意力头、每头 128 维；KV 压缩维度为 512，解耦 RoPE 维度为 64。把这些数字代入：

```text
MHA = 2 × 16 × 128 × 27       = 110,592 个元素 / token
MLA = (512 + 64) × 27         = 15,552 个元素 / token
```

在相同的 16 个头、每头 128 维、27 层的容量口径下，FP16/BF16（每元素 2 bytes）的理论缓存如下。GQA 与 MQA 行用于说明不同 KV 共享粒度，不代表这些注意力配置的质量或延迟实测。

| 注意力形式 | 每 token 元素数（所有层） | FP16/BF16 每 token | 32K token 理论缓存 |
|---|---:|---:|---:|
| MHA，16 个 KV 头 | 110,592 | 216 KiB | 6.750 GiB |
| GQA，8 组 KV | 55,296 | 108 KiB | 3.375 GiB |
| MQA，1 组 KV | 6,912 | 13.5 KiB | 0.422 GiB |
| MLA，512 维 latent + 64 维 RoPE | 15,552 | 30.375 KiB | 0.949 GiB |

按这组尺寸，MLA 的 KV 张量约为 MHA 的 14.06%，也就是少约 85.94%，约等于 GQA 2.25 组的缓存量。计算只包含缓存元素本身；没有计入页表/分配器、临时张量、权重、批处理对齐、量化元数据等运行时开销，也不推断实际生成速度。

可运行的纯 Python 估算器在 `mla_cache_demo.py`。例如：

```bash
python mla_cache_demo.py --tokens 32768 --dtype-bytes 2
```

脚本允许调整 token 数与每元素字节数，复核表格所用的容量公式。它复现的是缓存算术，不是 MLA 前向实现或 GPU 基准测试。

## 4. 相比前作，新的地方在哪里

MHA 为每个头独立缓存 K/V；MQA 把所有 Query 头的 K/V 共享为一组；GQA 则在两者之间分组共享。它们通过减少 KV 头数降低缓存，代价是让不同 Query 头共享相同的 KV 表示。

MLA 采取了不同路线：先把所有头的 K/V 联合压缩到一个较小潜变量，再通过各头的投影参与注意力。它不是“把 MQA 再多压一点”，而是重新安排缓存表示；另以解耦 RoPE 保留位置通道，从而让低秩压缩和位置编码并存。DeepSeek-V2 论文把这种设计描述为：缓存量接近 GQA 2.25 组，同时在其报告的实验中保持了较强的注意力能力。

DeepSeek-V2 的注意力消融实验对 MHA、GQA、MQA 做了同规模 7B 对比，并在小型与大型 MoE 设定下比较 MLA 与 MHA。论文报告后者的 KV Cache 分别约为 MHA 的 14% 与 4%，四项所列基准中结果接近或更高。这些结果支持该论文的设计选择，但仍来自特定模型、训练流程和基准，不能推成“所有模型换 MLA 都不掉点”。

## 5. 代价与适用边界

1. **新增投影与潜变量瓶颈。** 下投影、上投影增加了参数与计算路径；固定维度 `d_c` 也限制可保存的信息。更小的缓存不自动等于更低延迟，计算是否融合、硬件是否适配都很重要。
2. **位置路径仍占缓存。** RoPE Key 必须按 token 保留，公式中 `d_h^R` 不能漏算。更换 RoPE 处理方式或张量布局时，要重新评估缓存和内核兼容性。
3. **实现与调优更复杂。** 运行时要正确组织 latent、位置 Key 与 Query/输出投影。朴素地把所有头的 K/V 还原成完整张量，会丢失 MLA 的设计优势；高效实现需要适配 MLA 的注意力计算路径。
4. **整体模型对比存在混杂因素。** DeepSeek-V2 报告的整模型相对 DeepSeek 67B“KV Cache 减少 93.3%、最大生成吞吐提高 5.76 倍”是端到端系统对比。报告还提到线上服务采用 FP8 权重和平均 6-bit KV 量化，因此这两个数字不能单独归因于 MLA。

MLA 适合 KV Cache 是推理服务主要瓶颈、且团队能承担模型训练与推理内核适配成本的场景。若模型固定为传统 MHA 权重，不能仅把缓存格式替换成 MLA：它改变了注意力投影结构，需要相应模型参数与计算实现。
